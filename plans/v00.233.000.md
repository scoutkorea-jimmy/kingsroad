# v00.233.000 — 데이터 사라짐 사고 케이스 스터디 + lint 룰 항구 차단

## 사용자 요청
> 다음턴에 진행하고 유사한 문제가 두번다시 발생하지 않도록 케이스 스터디도 하고
> 기록에 남겨놔

직전 사이클 v00.231 의 23곳 가드는 발생한 인스턴스 수정. 본 사이클은 **재발
방지** — lint 룰 자동 차단 + 영구 문서화 + 미래 Claude 세션 메모리.

---

## 1. 사고 요약

**증상**: 사용자 보고 — "데이터들이 자꾸 간혹 사라진다. 이거 제일 중요하다."
구체적으로 강연·투어·칼럼·게시글·책 등 D1 source-of-truth 영역의 항목들이
화면에서 사라졌다가 새로고침하면 돌아오거나, 재발하거나.

**영향 범위**: 23개 `BGNJ_*` 도메인 헬퍼 — `LECTURES`, `TOURS`, `COLUMNS`,
`BOOKS`, `BOOK_ORDERS`, `COMMUNITY`, `FAQ`, `AUDIT`, `SITE_CONTENT`, `AUTH`.
사실상 사이트 전 운영 데이터.

**중대도**: 매우 높음 — 사용자/회원이 "데이터 신뢰성" 자체를 의심하게 만드는
유형의 버그. 단일 화면 깨짐보다 훨씬 심각.

## 2. 근본 원인 (Root Cause)

### 안티패턴

```js
// data.js — 사이트 전반에서 23곳 동일 패턴
async refresh() {
  try {
    const { lectures } = await window.BGNJ_API.lectures.list();
    this._lectures = (lectures || []).map(this._toLecture);  // ← 폭탄
  } catch {}  // ← 침묵
}
```

`(lectures || []).map()` 의 의도는 "응답이 falsy 면 빈 배열로 안전하게 처리".
**그러나** 빈 배열을 캐시에 할당하면 **이전에 정상 보유 중이던 데이터를 덮어쓴다**.

### 발화 조건

1. **워커 일시 오류** — D1 일시 throttling, KV 동기화 지연 등으로 워커가
   `{ lectures: null }` 응답.
2. **응답 키 mismatch** — 워커 리팩토링으로 `{ items: [...] }` 같이 키가
   바뀌면 클라이언트는 `lectures` 가 undefined → `[]` 로 캐시 초기화.
3. **다탭 broadcast race** — 어드민 탭에서 변경 → `BGNJ_BROADCAST.publish()`
   → 모든 탭이 `refresh()` 호출. 그 중 한 탭의 세션 만료/네트워크 일시 끊김 →
   잘못 파싱된 응답 → 빈 배열 덮어쓰기.
4. **catch 침묵** — 모든 케이스에서 `catch {}` 가 silent. 어드민/사용자
   누구도 "어디서 깨졌는지" 모른 채 데이터만 사라짐.

### 왜 미발견됐는가

- **테스트 부재** — refresh 헬퍼 단위 테스트 없음. 정상 응답 path 만 검증됨.
- **개발 환경 신뢰성 높음** — 개발자가 보는 워커 응답은 항상 정상이라
  null 응답을 만나기 어려움.
- **간헐 발생** — 항상 재현 안 되는 race/일시 장애 → 디버깅 불가.
- **silent fail** — 콘솔 경고 없으니 어드민도 사용자도 단서 못 잡음.
- **패턴 복제** — 한 헬퍼 작성 시 같은 컨벤션을 23개 다른 헬퍼에 반복.

## 3. 수정 (v00.231)

### 인스턴스 수정 (23곳)

```js
// Before
this._lectures = (lectures || []).map(this._toLecture);

// After
if (!Array.isArray(lectures)) {
  try { console.warn('[BGNJ_LECTURES.refresh] non-array — cache preserved'); } catch {}
  return this._lectures.slice();
}
this._lectures = lectures.map(this._toLecture);
```

3가지 효과:
1. **데이터 보존** — 비-배열 응답은 무시, 캐시 유지.
2. **silent fail 가시화** — `console.warn` 으로 어드민/디버깅 시 즉시 식별.
3. **정상 빈 응답 통과** — `Array.isArray([])` 는 true 이므로 사용자가 모든
   데이터를 의도적으로 삭제한 케이스는 정상 처리.

대상 (data.js 라인 번호 기준):

## 4. 재발 방지 (v00.233)

### 4.1 lint 룰 항구 차단

`tools/check-syntax.mjs` 에 신규 룰 `cache_overwrite`:

```js
{
  name: "cache_overwrite",
  allow: new Set([]),
  pattern: /\(\s*\w+\s*\|\|\s*\[\]\s*\)\.map\b/,
  msg: "(data || []).map() 금지 — 비-배열 응답이 캐시를 빈 배열로 덮어쓰는 \
        데이터-사라짐 안티패턴 (v00.231 사고). Array.isArray(data) 가드 후 \
        data.map(...) 사용",
}
```

pre-commit 훅이 자동 실행. 누군가 같은 패턴을 다시 도입하면 **커밋 자체가
차단**. 불가피한 경우 `// bgnj-lint-ignore-next-line cache_overwrite` 마커로
1줄 우회 (의도 명시 강제).

부수 발견 — 새 룰 추가 시 추가로 2곳 적발:
- `pages/CommunityPage.jsx:1498` — 댓글 멘션 자동완성 author 추출
- `pages/admin/AdminShared.jsx:298` — Sankey 다이어그램 rows 변환

이 둘은 캐시 덮어쓰기는 아니지만 **같은 코딩 습관** 이라 함께 `Array.isArray`
패턴으로 정정.

### 4.2 운영 가드 문서화

`CONTEXT.md §6` 사용자 가드 "항상 적용" 항목 추가:

> **데이터 캐시 덮어쓰기 (v00.231 사고 → v00.233 lint 룰)**: API 응답 →
> `BGNJ_*` 메모리 캐시 갱신 시 반드시 `Array.isArray(data)` 검증 후
> `data.map(...)`. `(data || []).map(...)` 패턴 절대 금지 — 비-배열 응답
> (null/undefined/object) 이 캐시를 빈 배열로 덮어써 사용자에게 "데이터
> 사라짐" 으로 보임. catch 블록에는 `console.warn('[BGNJ_X.method] non-array
> — cache preserved')` 진단 로그 추가. lint 룰 `cache_overwrite` 가
> pre-commit 자동 차단.

## 5. 학습 (Lessons)

### A. "안전한 폴백" 이 위험할 수 있다

`x || []` 패턴은 "값이 없으면 빈 컬렉션" 이라는 직관에 부합. 하지만
**캐시 갱신 맥락** 에서는 "값이 없으면 무시 (이전 캐시 유지)" 가 정확한
의미여야 한다. 두 의미가 같은 문법으로 표현되니 혼동 발생.

→ **언어/도구 차원 가드 (lint) 가 인간 검토보다 훨씬 효과적**. 23곳을 코드
리뷰로 잡는 건 사실상 불가능. 정규식 한 줄로 영구 차단.

### B. silent catch 는 "은닉된 손실"

`} catch {}` 는 "에러는 무시하고 계속" 이라는 의도지만 실제로는 "장애가
조용히 누적" 된다. 최소한 `console.warn` 으로 가시화해야 한다.

→ **catch 블록은 비어있을 수 있어도 진단 로그는 비어있으면 안 된다**.

### C. 패턴 복제는 버그 곱셈

한 안티패턴이 23곳에 복제 → 단일 fix 가 23x 의 가치.
**역으로 새 패턴 도입 시 같은 곱셈 위험**. 코딩 컨벤션은 lint 로 강제.

### D. 데이터 신뢰성 > 기능 풍부성

사용자는 "신청 폼이 한 칸 부족" 보다 "내 데이터가 사라짐" 에 훨씬
민감. 이번 사이클에서 사용자가 큰 신기능 4개 요청 중에도 "이거 제일
중요하다" 라고 표시한 것이 데이터 보존 이슈.

→ **운영 데이터 무결성** 은 모든 신기능보다 우선순위 높다.

## 6. 이후 audit 후보 (별도 사이클)

- **fire-and-forget save** — `BGNJ_FAQ.update()`,
  `BGNJ_SITE_CONTENT.saveSection()`, `BGNJ_COMMUNITY.updateReportStatus()`
  등 admin 패널의 await 없는 호출. silent fail 시 사용자가 "저장됐다"고 착각.
  await + try/catch + toast 패턴으로 sweep.
- **세션 만료 UX** — `BGNJ_AUTH.refreshSession` 이 401 시 캐시 비움 → 다른
  도메인 refresh 가 일제히 401 → silent. 만료 시 명시적 재로그인 안내 필요.
- **워커 응답 형식 lock** — D1 결과를 그대로 반환하지 말고 항상
  `{ items: [...], count: N }` 같이 wrap. 빈 결과도 명시적.
