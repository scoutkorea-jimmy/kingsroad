## 1. 지시 내역 (사용자 원문 요지)

1. 최상단에 `CLAUDE.md` 를 만들고, `rules/` 폴더를 신설해 **모든 규칙을 그 안에** 둔다.
   목적은 효율 — Claude 가 사이트 전체를 뒤지지 않고 **적절한 규칙 파일과 행 위치를 찾아** 확인하게 한다.
2. 모든 작업은 `rules/` 에 **handoff 문서**를 만들어 업무 지시 내역을 기록하고, 작업을 시작하고, 끝나면 **작업 완료로 기록**한다.
   이유: **PC가 바뀌어도 끊김 없이 업무를 잇기 위함.**
3. **디자인 디렉토리**를 만들고 홈페이지 전체 UI를 개편한다.
4. 사진은 **모두 관리자 페이지에서 올리고 관리**할 수 있게 한다. **지금은 비운 채로** 넣는다.

### 확정된 선택 (브레인스토밍 결과)

| 질문 | 결정 |
|---|---|
| `rules/` 구성 | 기존 문서를 **주제별로 쪼개서 이동**. `CLAUDE.md` 는 라우팅 표만 |
| handoff 단위 | **`plans/` 를 흡수** — 한 곳에서 지시→진행→완료 기록 |
| 디자인 디렉토리 | `design/` 폴더 **+** 디자인 스킬 연결 (둘 다) |
| 작업 범위 | 구조 재편 + UI 개편을 **한 사이클**로, 단 단계마다 커밋 |
| 히어로 방향 | **A안 — 사진 중심**. 사진 없으면 여백형으로 자동 폴백 |

### 보류 (사용자가 나중에 계획을 준다고 명시)

- **메뉴 체계 개편 전체.** 라벨·URL·그룹핑 모두 현행 유지.
- `/eat`(먹고 놀자) · `/shop`(사고 놀자) 삭제 — 한 번 지시됐다가 "메뉴 구성은 나중에 다듬자" 로 보류됨.
- → 사용자가 "삭제할 것 / 합칠 것" 계획을 주면 그때 별도 handoff 로 진행.

### 파트 2 — UI 개편 (4단계, 각 단계 끝에 커밋)

실제 화면(데스크톱 1440 / 모바일 390) 점검에서 확인된 문제:

1. 오버레이 3겹(상단 공지 바 + "NEW BUILD AVAILABLE" 패널 + 쿠키 카드)이 히어로를 덮음. 모바일에선 업데이트 패널이 로고를 가리고 공지 문장이 잘림.
2. 히어로 둘째 줄 "한국을" 이 통째로 옐로우 — **자체 원칙(옐로우 5% 면적, 인터랙션 전용) 위반**.
3. 배경 일러스트가 본문 텍스트 밑을 지나가 대비·가독성 저하.
4. 첫 화면에 빈 상태 2개 노출 ("예정된 강연이 아직 없습니다" / "예정된 답사가 아직 없습니다").
5. 지표 자리에 "준비 중" 문구. 모바일에서 3열이 좁아져 "여 행 지" 로 글자가 쪼개짐.

| 단계 | 내용 |
|---|---|
| **1. 첫 화면 되찾기** | 공지 바는 닫으면 기억 · 업데이트 패널을 구석 작은 토스트로 강등 · 쿠키 배너 높이 축소. 히어로가 첫 화면에 온전히 보이게 |
| **2. 히어로 A안 + 관리자 사진 관리** | 일러스트 제거, 사진 풀블리드 구조. 옐로우는 CTA 하나에만. **사진 0장이면 여백형으로 자동 렌더** → 코드 수정 없이 사진만 넣으면 A로 승격. 관리자에 히어로 사진 관리 신설(업로드·순서·교체·삭제), `siteContent` 에 목록 저장. **지금은 비운 채로 출시** |
| **3. 홈 나머지 정리** | 데이터 없는 섹션은 빈 상태 대신 **섹션 자체 숨김**. 지표에서 "준비 중" 제거, 모바일 3열→2열 |
| **4. 전역 시각 시스템** | 옐로우 5% 룰 lint 강제 · 타이포 스케일 정리 · 모바일 규칙 점검 |

## 3. 사진 자산 실측 (2026-07-29 조사 — 결론의 근거)

| 자산 | 수량 | 실측 폭 |
|---|---|---|
| 커뮤니티 게시글 이미지 | 497장 | **510px** (표본 7장 중 5장이 정확히 510) |
| 칼럼 커버 | 74장 | 462~800px, 1668px 1장 |

- 폭 510px 반복 = 네이버 블로그 본문 기본 폭. **원본이 아니라 웹에서 복사해온 이미지**로 보임. 클라이언트 리사이즈 코드는 없음(확인함) → 재업로드해도 커지지 않음.
- 가장 큰 1668px 칼럼 커버는 사진이 아니라 "풍수지리(風水地理)" 개념 설명 **일러스트 카드**.
- 칼럼 커버 표본 중 하나는 Exif 에 `Gyeongbokgung Palace in sunset is beautiful, Seoul, South Korea.` — **스톡 사진 설명문**. 히어로처럼 눈에 띄는 자리에 쓰면 저작권 문제가 실제로 불거지는 위치.
- 커뮤니티 사진 내용 자체는 좋음(실제 답사 능선 풍경). 다만 510px + 회원 업로드라 히어로 사용에 동의 필요.

**→ 그래서 "A 구조 + 빈 사진 슬롯 + 관리자 업로드" 로 결정됨.** 히어로용은 가로형 3~5장, 폭 2000px 이상 권장.

## 4. 기술 확인 사항 (조사 완료)

- **워커 배포 불필요.** `POST /api/media/upload` 가 `folder` 를 받고, `USER_ALLOWED_FOLDERS`(`post-images` / `post-attachments` / `lecture-covers` / `tour-covers`)에 **없는** 폴더는 자동으로 admin 전용. → `hero-images` 는 워커 수정 없이 관리자 전용 업로드가 됨. ([workers/src/index.js:752](../../workers/src/index.js#L752))
- 업로드 헬퍼 `pickImageWithR2Fallback` 이 `AdminShared.jsx` 에 이미 있음. `AdminSiteContentPanel.jsx` 의 `ImageUploader` 는 **단일 필드**용 → 히어로는 **목록 관리 UI 가 새로 필요**.
- `siteContent` 는 D1 `siteContent_kv` 로 서버 저장 → 히어로 사진 목록도 여기 저장.
