## 3. 개편안

### 메뉴 (7개 → 5개)

```
홈 │ 자고 놀자 │ 답사·투어 │ 배움 ▾ │ 커뮤니티 ▾
                              ├ 강연      ├ 자유 · 질문 · 정보 · 공지
                              └ 도서      ├ 뱅기노자 칼럼      ← 메뉴 이동
                                          ├ 한켠역사문화포럼    ← 신설(사용자 작업)
                                          └ 언론보도
```

**URL 은 전부 유지한다** (`/lectures` `/book` `/column` 각각 살림).
메뉴만 묶고 통합 페이지에서 탭 전환. 이유 — 칼럼 72편의 검색 유입과 `#col-N` 앵커가 안 깨지고 구현 위험이 낮다.

### 우하단 위젯

```
                    ┌──────────────┐
                    │ 무엇을 도와  │
                    │ 드릴까요?    │
                    │ ▸ 가장 빠른 강연 일정 │
                    │ ▸ 가장 빠른 답사 일정 │
                    │ ▸ 가장 최근 칼럼     │
                    └──────────────┘
                              [↑]  ← Top (위로 밀림)
                              [💬] ← 챗봇 (신규)
```

**AI 없음.** 이미 메모리에 있는 헬퍼를 읽어 정해진 답을 만든다. 서버 호출·비용·지연 0.

**핵심 설계 판단 — 예정이 0개인 현실을 전제로 만든다.**
그냥 만들면 3개 중 2개가 "없습니다"로 끝난다. 그래서:

> 예정 있으면 → 제목 + 날짜 + `보러 가기`
> 예정 없으면 → "지금 예정된 강연은 없습니다. 지난 강연 N회 기록을 보실 수 있어요" + `지난 강연 보기`

**빈손으로 돌려보내지 않는 것이 이 위젯의 존재 이유다.**

## 11. 열 때마다 옛 사이트가 보이던 문제 (v00.294.011 ~ .012 — 완료·배포됨)

사용자 보고 '사이트를 열면 과거 임시 사이트나 임시 문구가 보인다'.

### 원인 — 자산은 캐시버스팅하는데 **그 목록을 적어 둔 HTML 이 캐시된다**

GitHub Pages 는 `index.html` 에도 `Cache-Control: max-age=600` 을 준다(실측).
`?v=` 로 자산은 새로 받게 만들었지만, **그 `?v=` 값을 담은 HTML 자체가 10분 캐시**되므로
재방문자는 최대 10분간 옛 HTML → 옛 번들 → **옛 화면을 통째로** 본다.
배포가 잦은 날엔 거의 매번 걸린다. Pages 는 응답 헤더를 못 바꾼다 → 클라이언트에서 끊어야 한다.

### 조치

새 버전 감지 시 **안전할 때 자동으로 한 번** `?_v=<새버전>` 으로 새로고침.
안전하지 않으면 종전대로 배너. 같은 버전은 세션당 1회(무한루프 차단).

### 시험하지 않았으면 못 잡았을 것 — .011 은 한 번도 발동하지 않았다

'작성 중일 수 있으니 막는다' 를 `[role="dialog"]` 존재로 판정했는데
**쿠키 동의창이 `role="dialog"`** 였다. 동의 전 방문자(=첫 방문·쿠키 지운 재방문자,
정확히 이 기능이 필요한 사람들)는 영영 안 걸렸다.
→ **'잃을 것이 있는 모달' 만** 막는다: 안에 textarea·contenteditable·
(checkbox/radio 아닌) input 이 있는 경우만. Tiptap 은 textarea 가 아니라
contenteditable 이라 '값 있는 입력' 검사에도 안 걸렸다 — 그것도 함께 본다.

로컬에서 version.json 을 높게 두고 확인: 자동 1회 ✓ / 이후 반복 없음 ✓ / 작성 중 차단 ✓

### 남은 한계 · 확인 필요

- 이 수정은 **새 HTML 을 받은 방문자부터** 적용된다. 이미 옛 HTML 을 문 브라우저는
  옛 코드를 돌리므로 이번 한 번은 배너 동작이다. 이후부터 자동.
- ~~상단 오픈 안내 배너 확인 대기~~ → **v00.294.013 에서 내렸다** (사용자 요청).
  `DEFAULT_SITE_CONTENT.banner.enabled: false`. 서버에 `banner` 섹션이 없어
  이 코드 기본값이 곧 운영 값이다(확인함).
  **문구는 지우지 않았다** — 관리자 → 사이트 콘텐츠에서 켜기만 하면 그대로 돌아온다.
  '기본값 복원' 을 해도 이제 꺼진 상태가 기본이다.

## 15. Safari 사용자는 로그인해도 아무것도 못 하고 있었다 (v00.295.003 — 완료·배포됨)

사용자 제보: 회원(김유미)이 광장 글에 사진을 첨부하려는데 계속 에러.

### 추측하지 않고 기록을 봤다

`error_log` 에 그대로 남아 있었다. 2026-08-21 00:43~00:49(UTC), `/community`, 7건.

```
'38570F99-F66B-4BE5-9547-EB8F162266F1.jpeg' 업로드 실패 — (로그인이 필요합니다.)
user_id: NULL · origin: https://bgnj.net
UA: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_6) ... Version/15.5 Safari/605.1.15
```

크기도 확장자도 아니고 **401**. `user_id` 가 NULL — 서버는 세션을 아예 못 봤다.
`sessions` 를 보니 같은 시각에 **네 번 로그인**했다(00:38 · 00:46 · 00:47 · 00:48).
로그인 → 업로드 401 → 다시 로그인 → 또 401 을 네 번 반복한 것이다.
**홍준기 님도 3연속 로그인 흔적**이 있다 — 같은 일을 겪은 것으로 보인다.

### 근본 원인 — 인증이 cross-site 쿠키 하나에만 매달려 있었다

사이트는 `bgnj.net`, API 는 `banginoja-api.scoutkorea.workers.dev`. **서로 다른 사이트**다.
그래서 세션 쿠키는 third-party 쿠키이고, **Safari 는 13.1(2020)부터 이를 전면 차단**한다.
`SameSite=None; Secure` 를 붙여도 소용없다 — 그건 차단을 푸는 스위치가 아니다.

**서버는 원래부터 `Authorization: Bearer` 를 지원했다**(`readSessionToken` 이 쿠키보다 먼저 본다).
그런데 라우트가 `json({ user })` 로 **토큰을 응답에서 버리고** 있었고, 클라이언트도 헤더를 안 붙였다.
그래서 서버에 준비된 길이 있는데 아무도 그 길로 가지 않았다.

**화면은 왜 로그인처럼 보였나** — 로그인 응답 본문의 `user` 로 `bgnj_session_user` 캐시가 채워진다.
새로고침 전까지는 로그인 상태로 보인다. 그래서 글쓰기 폼까지 들어가고 업로드에서야 튕겼다.

### 고친 것

- 워커: `/auth/login` · `/auth/signup` 응답 본문에 `token` 을 함께 실어 보낸다. **쿠키도 그대로 내려보낸다.**
- `api.js`: 토큰을 `localStorage.bgnj_session_token` 에 두고 모든 요청에 `Authorization: Bearer`.
  401 이 오면 죽은 토큰이므로 버린다. 로그아웃은 서버 호출이 실패해도 `finally` 로 반드시 버린다.
- CORS 는 손댈 필요가 없었다 — `Access-Control-Allow-Headers` 에 `Authorization` 이 이미 있다(실측 확인).

### 검증 — 시험 계정으로 전 경로를 돌리고 지웠다

**쿠키를 일부러 저장하지 않고**(= Safari 상황 재현) 확인했다.

| | 결과 |
|---|---|
| ① 가입 응답에 token | ✅ 포함됨 |
| ② 쿠키 없이 Bearer 만으로 업로드 | ✅ 성공 (`post-images/…jpg`) |
| ③ 토큰 없이 같은 요청 | `{"error":"로그인이 필요합니다."}` — 제보된 증상 그대로 재현 |

정리 완료: R2 객체 삭제 · 시험 계정/세션/로그인시도 삭제 · 잔여 0건 확인(회원 15명 그대로).

### 남은 한계 · 다음 할 일

- **Safari 사용자는 한 번 다시 로그인해야 한다.** 지금 브라우저에 토큰이 없기 때문이다.
- `localStorage` 토큰은 httpOnly 쿠키보다 XSS 에 약하다. **근본 해결은 API 를 `api.bgnj.net` 에 두는 것** —
  그러면 same-site 가 되어 쿠키가 정상 동작한다. `bgnj.net` 은 이미 Cloudflare DNS 를 쓰므로(ns 확인)
  워커 커스텀 도메인만 붙이면 된다. **Bearer 경로는 그때도 방어선으로 남긴다.**
- **별건으로 눈에 띈 것** — `/tour` 에서 관리자 커버 이미지 업로드가 5건 실패해 있다
  (`이미지가 너무 큽니다(6.0MB). R2 실패 + 1.5MB 폴백 한도 초과`, 2026-08-20 Windows).
  이번 401 과는 다른 건이다. 손대지 않았다.

`api.bgnj.net` 이면 same-site 라 Safari 도 first-party 로 취급한다.

- `wrangler.toml` 에 `[[routes]] pattern = "api.bgnj.net" / custom_domain = true`
- CSP `connect-src` 에 새 주소 추가. **이걸 빼면 모든 호출이 차단된다** — 바꾸기 전에 반드시 같이 연다.
- CORS 는 손댈 것 없음. preflight 실측으로 `Authorization` 허용 확인.
- **옛 주소도 살려 둔다.** 이미 올라간 이미지 URL 이 workers.dev 로 DB 에 박혀 있고,
  옛 코드를 문 브라우저도 남아 있다.
- Bearer 토큰(v00.295.003) 덕분에 **주소가 바뀌어도 재로그인이 필요 없다** — 토큰은 localStorage 에 있고
  `sessions` 는 그대로다.

### ⚠ 사고 — 배포 직후 약 1~2분 사이트가 끊겼다

`wrangler.toml` 에 **`workers_dev` 를 명시하지 않으면 wrangler 가 workers.dev 를 꺼 버린다.**
경고로만 알려주고 그대로 진행한다. 배포 직후 옛 주소가 404 가 됐고, 그때 사이트가 쓰던 주소가 그거였다.

```
▲ WARNING  Because 'workers_dev' is not in your Wrangler file, it will be disabled for this deployment
```

- 배포 직후 **양쪽 주소를 curl 로 찍어 보고 바로 발견**해 `workers_dev = true` 를 넣고 재배포했다.
- 복구 후에도 옛 주소가 두어 번은 404 였다 — 전파에 몇 초 걸린다. 한 번 찍고 판단하면 안 된다.
- `wrangler.toml` 에 이 줄을 지우면 안 되는 이유를 주석으로 박아 뒀다.

### ② 큰 사진 줄이기 — 물어보고 줄인다 (사용자 선택)

`components/ImageShrink.jsx` 신설. 붙인 곳 셋 — 광장 첨부 이미지 · 본문 에디터(붙여넣기/버튼) · 관리자 커버.

- **먼저 줄여 본 뒤 물어본다.** '5.8MB → 0.9MB 로 줄여서 올릴까요?' 예측이 아니라 실제 결과라 판단이 된다.
- **여러 장이면 한 번만 묻는다.** 열 장 고르고 열 번 확인창이 뜨면 그게 더 나쁘다.
- **EXIF 방향** — 캔버스로 다시 그리면 회전 정보가 날아가 사진이 눕는다.
  `<img>` 를 거치면 브라우저가 EXIF 를 적용해 렌더하므로 바로 선 상태로 그려진다.
  `createImageBitmap` 의 `imageOrientation` 은 Safari 지원이 늦어 안 쓴다.
- **GIF 는 안 건드린다** — 다시 그리면 움직임이 죽는다.
- **PNG 는 흰 바탕을 깔고 JPG 로** — 투명이 검게 나오는 것을 막는다. 확인창에 이 사실을 알린다.
- 줄인 게 원본보다 크면 버린다(이미 잘 압축된 작은 사진).
- **못 올리는 이유를 두 갈래로 안내한다** — 줄일 수 있었는데 원본을 고른 경우와,
  GIF·HEIC 처럼 아예 줄일 수 없는 형식인 경우. 처음엔 뭉뚱그려 썼다가 시험에서 부정확한 걸 잡았다.

이것으로 2026-08-20 관리자 커버 5연속 실패(`6.0MB`)도 해결된다 — 원인은 401 이 아니라 5MB 한도였다.

### 검증

- 새 주소: preflight 204 + `Authorization` 허용, GET 200 + CORS 헤더 실측.
- 축소 판단 로직: 실제 파일 텍스트를 떼어 Node 에서 실행.
  작은 사진은 묻지 않고 통과 ✅ / 큰 GIF 는 안 건드리고 통과 ✅ / 한도 넘는 GIF 는 차단 + 형식별 안내 ✅
- **캔버스 축소 자체는 브라우저에서만 돌아간다 — 눈으로 확인 못 했다.** 사용자 확인 필요.

## 17. 사진을 올렸는데 글에 안 들어갔다 (v00.295.005 — 완료·배포됨)

사용자 보고: 글은 올라갔는데 이미지가 안 보인다. 실제로 100번 글 `images_json` 이 `[]` 였다.

### 어디서 사라졌는지부터 갈랐다

- **이미지 파일 자체는 멀쩡하다** — 기존 글의 이미지 URL 을 찍어 보니 옛/새 주소 양쪽 200 · 6.8MB 정상.

### 원인 — 첨부가 목록에 들어가기 전에 게시할 수 있었다

사진은 '고르는 순간' 이 아니라 **축소 확인 + 업로드가 끝난 뒤** 에야 `images` 에 들어간다.
그 전에 게시하기를 누르면 첨부가 통째로 빠진 채 저장된다. 막는 장치가 없었다.

### 고친 것

- `ImageAttacher` · `FileAttacher` · `TiptapEditor` 가 **처리 중임을 부모에 알린다**(`onBusyChange`).
- `PostCompose` 는 셋 중 하나라도 처리 중이면 **게시 버튼을 잠그고** '사진 올리는 중…' 을 보여준다.
  submit 에도 같은 가드를 둔다 — 버튼만 잠그면 엔터 제출로 빠져나간다.
- 이미지 선택 버튼도 처리 중엔 잠근다. 연달아 누르면 상태가 엉킨다.

### 아직 확정 못 한 것

**사용자가 실제로 어떤 순서로 했는지는 모른다.** 재현 정보를 못 받은 상태에서
'여기가 유일하게 비어 있을 수 있는 자리' 를 막은 것이다. 같은 일이 또 나면 다른 원인이 있다는 뜻이다.
그때는 발행 시점의 `images` 개수를 남기는 진단을 붙여야 한다.

## 19. 검색·AI 크롤러가 사이트를 읽을 수 있게 (v00.296.000 — 완료·배포됨)

사용자 지시 '모든 것들을 AI 친화적으로. 특히 구글 봇과 네이버 봇이 쉽게 찾을 수 있게'.

### 실측한 출발점 — 검색엔진에게 이 사이트는 빈 페이지였다

| 확인 | 결과 |
|---|---|
| `bgnj.net/community` · `/column` · `/book` · `/tour` | **전부 HTTP 404** |
| 크롤러가 받는 HTML 본문 | **231자** ("JavaScript로 렌더링됩니다" 가 전부) |
| sitemap.xml 에 적힌 10개 주소 | 그중 9개가 404 |
| 글 88편 · 칼럼 72편 | 하나도 등록돼 있지 않음 |

GitHub Pages 는 없는 경로에 `404.html` 을 **404 상태로** 준다. SPA 복원용으로 만든 그 파일이
크롤러에게는 '이 주소는 없다' 는 신호였다. sitemap 은 색인을 돕기는커녕 죽은 링크 목록이었다.

그리고 구글봇은 JS 를 돌려 결국 보지만, **네이버봇(Yeti)과 AI 크롤러(GPTBot·ClaudeBot·PerplexityBot)는
JS 를 돌리지 않는다.** 그들에게 이 사이트에는 아무 내용도 없었다.

### 고른 방법 — 정적 생성(프리렌더)

Cloudflare 프록시가 꺼져 있어(실측: `server: GitHub.com`, CF 헤더 없음) 워커를 사이트 앞에 끼울 수 없다.
그래서 빌드 때 **주소마다 진짜 내용이 담긴 `index.html` 을 만든다** — `tools/seo-build.mjs`.

- 내용은 `<div id="root">` **안에** 넣는다. React 가 부팅하며 그대로 덮어쓰므로
  사람에게는 지금과 똑같은 SPA 이고, 크롤러에게만 읽을 것이 생긴다. **클로킹이 아니다**(같은 내용).
- 결과: 본문 231자 → 홈 614자 · 광장 목록 3,822자 · 칼럼 목록 8,390자 · 글 상세 1,175자.
- 170개 주소(정적 10 + 글 88 + 칼럼 72) 생성. sitemap.xml 도 여기서 자동 생성한다.
- JSON-LD 구조화 데이터 — 홈은 Organization+WebSite, 목록은 CollectionPage, 글은 Article.
- canonical · og:url 을 주소마다 정확히 박는다.

### 함정 셋 — 다음 사람을 위해

1. **상대경로를 절대경로로 바꿔야 한다.** `/community/98/index.html` 에서 `src="dist/app.js"` 는
   `/community/98/dist/app.js` 를 찾아 화면이 통째로 안 뜬다. `absolutize()` 가 이걸 한다.
2. **인라인 `<script>` 를 새로 넣으면 안 된다.** CSP 가 인라인 스크립트 SHA-256 해시를 못 박아 둔다.
   그래서 글 번호는 `<body data-bgnj-post="98">` 속성으로 넘기고 `boot.jsx` 가 읽는다.
3. **멱등이어야 한다.** index.html 이 곧 템플릿인데 홈을 그 자리에 덮어쓴다.
   첫 판은 재실행하면 JSON-LD 가 2→3 으로 쌓이고 `#root` 정규식이 안 맞아 홈이 **조용히 갱신 안 됐다.**
   `normalize()` 로 먼저 원상복구하게 고쳤고, **3회 연속 실행해 결과가 같은 것을 확인**했다.

### 빌드 순서를 지켜야 한다

```
node tools/csp-hashes.mjs   →   node tools/build.mjs   →   node tools/seo-build.mjs
```

`seo-build` 가 **반드시 마지막**이다. 순서를 바꾸면 index.html 만 새 해시를 갖고
하위 170개는 옛 해시를 물어 CSP 로 통째로 차단된다.

### robots.txt · llms.txt

- 네이버 `Yeti` · 다음 `Daumoa` 를 이름으로 명시. **같은 줄 주석은 뺐다** — 표준상 허용이지만
  파서에 따라 User-agent 값이 오염될 수 있다.
- AI 크롤러 11종 명시 허용(GPTBot · ClaudeBot · PerplexityBot · Applebot · CCBot 등).
- `llms.txt` 신설 — AI 에게 사이트 구조·주요 주제·인용 정책을 한 장으로 알린다.

### 남은 것

- **글을 새로 쓰면 정적 페이지가 자동으로 안 생긴다.** `node tools/seo-build.mjs` 를 다시 돌려
  커밋해야 한다. GitHub Actions 로 하루 1회 자동화할 수 있다 — **사용자 판단 대기.**
- 구글 서치콘솔 · 네이버 서치어드바이저에 사이트를 등록하고 sitemap 을 제출해야 실제로 색인이 시작된다.
  **이건 사람이 계정으로 해야 하는 일이다.**

## 20. `<window.X/>` 로 쓰는 컴포넌트 11개가 등록돼 있지 않았다 (v00.296.001 — 완료·배포됨)

사용자 보고: 관리자 '한켠 예약' 탭에서 `Minified React error #130`.

### React #130 = '그리려는 컴포넌트가 undefined'

`AuthAdminPage.jsx:1190`

```jsx
{tab === "한켠 예약" && HangyeonAdminPanel && <window.HangyeonAdminPanel/>}
//                     ↑ import 한 것(정의됨)     ↑ window(undefined)
```

**가드는 import 를 보고 렌더는 window 를 본다.** 그래서 가드를 통과한 뒤 undefined 를 렌더한다.

### 뿌리 — v00.287 ESM 전환의 잔재

각 파일이 `window.X = X` 로 등록하던 것을 ESM export 로 바꾸면서 **등록만 사라지고
사용처는 `<window.X/>` 그대로 남았다.** `MediaGallery.jsx` 는 주석에 "window 병행" 이라고
적혀 있는데 실제 코드가 없었다 — 주석이 거짓말을 하고 있었다.

전수 조사: `<window.X/>` 로 쓰는 컴포넌트 **14개 중 11개가 미등록.**

| 미등록 | 정의 위치 |
|---|---|
| CoverPlaceholder · PastBoardList | `components/Shell.jsx` |
| MediaGalleryEditor · MediaGalleryView | `components/MediaGallery.jsx` |
| HangyeonAdminPanel | `pages/admin/HangyeonAdminPanel.jsx` |
| HeatmapGrid | `pages/admin/AdminShared.jsx` |
| KindPagePanel · LecturePageEditorPanel · TourPageEditorPanel | `pages/admin/AdminContentEditors.jsx` |
| LectureQuickAddModal | `pages/LecturesPage.jsx` |
| TourQuickAddModal | `pages/WangsanamTourPage.jsx` |

### 증상이 두 갈래라 더 늦게 발견됐다

| 가드가 보는 것 | 결과 |
|---|---|
| `{window.X && <window.X/>}` | **조용히 렌더 안 됨.** 오류도 없이 기능만 사라진다 — 관리자 한켠 탭의 사진 편집이 그렇게 없어져 있었다 |
| `{X && <window.X/>}` | **undefined 렌더 → React #130, 화면 전체 crash** — 한켠 예약 · 자고 놀자 · 강연/투어 페이지 편집 |

즉 **관리자 탭 여러 개가 깨져 있거나 기능이 비어 있었다.** 한켠 예약만의 문제가 아니었다.

### 고친 방법

사용처를 건드리지 않고 **정의 파일 끝에 `window.X = X` 를 복원**했다. 회귀 위험이 가장 작고,
각 파일이 주석으로 이미 약속하던 상태로 되돌리는 것이다. ESM export 는 그대로 둔다.

### 재발 차단 — `tools/check-globals.mjs`

`<window.X/>` 를 쓰는데 등록이 없으면 커밋을 막는다. `Object.assign(window, {...})` 형태도 등록으로 인정한다(AdminShared 가 그 방식).

- 만들고 나서 **일부러 위반 파일을 넣어 잡히는 것을 확인**하고 지웠다.
- pre-commit 훅에 `check-globals` · `check-hooks` 둘 다 추가했다.
  **둘 다 '오류 없이 화면만 깨지는' 종류**라 사람 눈으로는 늦게 발견된다 —
  실제로 각각 운영에서 터진 뒤에야 만들었다.

### 확인 못 한 것

**화면을 눈으로 보지 못했다.** 번들에 등록 코드가 실린 것은 확인했다
(`dist/admin.js` 에 `window.HangyeonAdminPanel=`, `dist/app.js` 에 `window.MediaGalleryEditor=`).
관리자 각 탭이 실제로 뜨는지는 사용자 확인이 필요하다.

v00.170 주석에 남아 있다 — '글 작성 후 본문 사라짐' 제보가 있었고,
상세 화면이 목록 캐시에서 본문을 읽고 있어서였다. 그때 목록에 body 를 실어 급히 막았다.

### 조치

- 워커: 목록 응답에서 `body` 제거, 대신 **태그를 걷어낸 발췌 400자**(`excerpt`)를 보낸다.

- 목록 검색이 `p.body.text` 를 보고 있었다(CommunityPage:659). 그대로 두면
  **본문 검색이 조용히 제목 검색으로 쪼그라든다.** 제목 + 전문(이미 연 글) + 발췌를 함께 보게 고쳤다.

**1,395KB → 116KB (12배).** 관리자뿐 아니라 **광장 목록과 홈 화면도 함께 가벼워진다** —
홈도 이 목록을 받고 있었다.

검증: 상세 API 가 본문 1,747자를 정상 반환 · 목록 응답에 `body` 없고 `excerpt` 있음 ·
images 6장 유지(📷 표시 산다) · 재측정 0.46~0.55초.

### 아직 안 한 것 — 다음 차례

- **칼럼 목록 463KB.** 이제 가장 큰 덩어리다. 같은 방식으로 줄일 수 있지만
  **칼럼에는 `_hydrate` 장치가 없다.** 새로 만들어야 하므로 '칼럼 본문 사라짐' 사고를 낼 위험이 있다.
  posts 패턴을 그대로 복제하면 되지만 **검증까지 하고 나서 배포해야 한다.**
- **② 관리자 초기 로딩 지연화.** ① 이후 남은 최대 덩어리가 칼럼이므로, 칼럼을 먼저 줄이는 편이 효과가 크다.
- **③ 이미 올라간 큰 사진 재압축**(26MB 글 1건) — 사용자가 '홍준기님 글은 상관없다' 고 하여 보류.

## 22. 칼럼 목록 축소 + 부팅 요청 정리 (v00.296.003 — ①② 완료·배포됨)

사용자 지시: '1번과 2번 진행. 3번은 하지 말자.'

### ① 칼럼 목록 463KB → 53KB (8.7배)

글 목록과 같은 방법. 다만 **칼럼에는 본문을 따로 받아오는 장치가 없어 새로 만들었다.**

- 워커: 목록 응답에서 `body` 제거. `excerpt` 컬럼이 원래 있고 72편 모두 채워져 있었다(최대 100자).
- `BGNJ_COLUMNS._hydrateColumnBody(id)` 신설 — 게시글의 `_hydratePostBody` 와 같은 모양.
- `ColumnPage` 가 상세 진입 시 호출. **이게 없으면 칼럼 본문이 빈 채로 보인다.**
- 검색은 손댈 필요 없었다 — `searchPublic` 이 이미 title·excerpt·body 를 함께 본다.

**함께 잡은 조용한 회귀** — 읽는 시간이 `c.body.text` 로 계산되고 폴백이 `c.readTime` 이었는데,
`_toColumn` 에 그런 필드가 없어 **늘 undefined** 였다. 본문을 빼는 순간 읽는 시간이 통째로
사라졌을 것이다. `readMinutes`(DB 컬럼) 폴백으로 고쳤다.

⚠ 배포 직후 크기가 안 줄어든 것처럼 보였다 — **CDN 캐시(s-maxage=60)** 였다.
60초 지나 재측정하니 53KB. **한 번 재고 판단하면 안 된다.**

### ② 부팅 요청 정리 — 관리자 페이지가 아니라 '부팅' 이 문제였다

관리자 화면을 열 때 새로 받는 건 회원 목록 하나뿐이다. 무거운 것들은 **앱 부팅 때** 이미 받는다.
그러니 ①이 곧 ② 였다. 그런데 부팅 코드를 열어 보니 더 큰 것이 있었다.

**모든 방문자에게 `includeHidden: true` / `admin: true` 를 붙여 보내고 있었다.**

- 워커의 `_publicCacheable` 은 이 옵션이 붙으면 캐시를 포기한다 →
  **방문자 한 명 한 명이 CDN 을 못 타고 워커+D1 까지 갔다.**
- 감춰 둔 콘텐츠가 내려갈 소지도 있었다. **서버가 이 옵션에 권한 검사를 하지 않았다.**
  실측해 보니 지금은 비공개 칼럼·숨김 강연/투어가 0건이라 **실제로 샌 것은 없었다.**
  하지만 비공개 칼럼을 하나 만드는 순간 새는 구조였다.

조치:
- 서버 `wantsHidden()` — `includeAll`/`includeHidden` 은 **관리자일 때만** 유효. 아니면 조용히 무시.
- 부팅은 **공개분만** 받는다. 관리자로 확인된 뒤(`refreshSession` 이후)에만 '숨은 것까지' 다시 받는다.
  대다수인 일반 방문자가 CDN 캐시를 타게 된다.

검증: 비로그인으로 `?includeAll=1` 요청 → 공개 72편만 · `cache-control: public, s-maxage=60` 정상.

### 최종 — 방문자가 부팅 때 받는 총량

| | 크기 |
|---|---|
| 작업 전 | **1,860 KB** |
| 지금 | **221 KB** (8.4배 ↓) |

여기에 CDN 캐시까지 살아나므로 두 번째 방문자부터는 워커까지 가지도 않는다.

### ③ 는 하지 않았다

이미 올라간 26MB 글의 사진 재압축 — 사용자 지시로 제외.

## 24. 내구 점검에서 나온 5건 전부 수정 (v00.296.005 — 완료·배포됨)

사용자 지시 '모두 다 진행'. **고친 뒤 같은 공격을 다시 걸어 확인**했다.

| 항목 | 전 | 후 (실측) |
|---|---|---|
| ③ 정원 초과 동시 예약 | 오버부킹 가능 | **정원 1석에 4명 동시 신청 → 확정 1 · 대기 3** ✅ |
| ④ 중복 주문 | 동시 3건이 3건 생성 | **동시 3건 → 실제 1건, 나머지는 같은 주문번호 반환** ✅ |
| ⑦ 악성 스크립트 | 그대로 저장 | **`<script>`·`onerror` 제거되어 저장** ✅ |
| ⑧ 초대형 본문 | 5MB 저장됨(201) | **413 차단** ✅ |
| ⑩ 글 도배 | 5회 전부 성공 | **1분 3건 초과 시 429** ✅ |

### ③④ 는 같은 병이었다 — '세고 나서 넣기'

```
① 몇 건인지 센다 → ② 판단한다 → ③ 넣는다
```
동시에 온 요청은 **둘 다 ①에서 같은 숫자를 본다.** 정원도, 중복 주문도 이 구조였다.
→ **한 문장으로 묶었다.** SQLite 는 단일 문장을 원자적으로 처리한다.
`INSERT ... SELECT ... CASE WHEN (SELECT COUNT(*) ...) >= capacity THEN 'waitlist' ELSE ... END WHERE NOT EXISTS (...)`
`meta.changes` 가 0이면 NOT EXISTS 에 걸린 것 — 중복 신청/중복 주문으로 판정한다.

**중복 주문은 한 번 헛짚었다.** 처음엔 '먼저 찾아보고 없으면 넣기' 로 만들었는데 시험해 보니
동시 3건이 그대로 3건 생성됐다. **같은 경쟁을 그대로 반복한 것이다.** INSERT 에 NOT EXISTS 를
붙여 다시 만들고 재시험해 통과했다. **고치고 나서 시험하지 않았으면 못 잡았다.**

투어 예약은 **중복 예약 검사조차 없었다** — 같은 사람이 같은 투어를 몇 번이든 잡을 수 있었다. 함께 막았다.

### 함께 잡은 것 — 본문이 통째로 날아가는 자리

시험하다 발견했다. 클라이언트는 본문을 HTML 문자열로 보내는데, 만약 `{ html, text }` 객체가 오면
`String()` 이 **`"[object Object]"`** 를 만들어 **본문이 사라진 채 저장된다.** 오류도 안 난다.
`body.html` 을 꺼내도록 막았다.

⚠ 이것 때문에 **첫 시험이 잘못됐다** — 객체로 보냈더니 15자로 줄어 길이 상한을 통과했다.
'상한이 안 먹는다' 고 판단할 뻔했다. **시험이 실제 사용과 같은 모양인지 먼저 봐야 한다.**

### 상한값

| 대상 | 상한 |
|---|---|
| 제목 | 200자 |
| 본문(게시글·칼럼) | 200,000자 |
| 댓글 | 5,000자 |
| 칼럼 요약 | 2,000자 |
| 작성 빈도 | 1분 3건 · 1시간 20건 (**관리자 제외** — 공지를 연달아 올리는 게 정상 업무다) |

빈도 검사가 DB 오류로 실패하면 **막지 않고 통과시킨다.** 도배 방지가 서비스 중단보다 중요하진 않다.

### ⑦ 은 보조 방어선이다

정규식으로 HTML 을 완전히 정화할 수는 없다. **주 방어선은 여전히 표시 단계의 DOMPurify(fail-closed)** 이고,
저장 단계는 그 한 겹이 뚫릴 때를 위한 두 번째 겹이다.

### 시험 흔적

시험 계정 5개 · 숨김 강연 1개(정원 1석) · 신청 4건 · 주문 4건 · 글 8편을 만들고 **전부 삭제**했다.
정리 후 확인: 글 89 · 회원 17 · 강연 3 · 주문 1 · 신청 0 · **시험 잔여 0**.

## 25. 🔴 글을 클릭하면 '해당 게시글을 찾을 수 없습니다' (v00.296.006 — 긴급 수정·배포됨)

사용자 보고. 광장에서 어느 글을 눌러도 상세가 안 열렸다. **내가 만든 사고다.**

### 원인 — 응답 껍데기를 벗기지 않았다

```js
const fullPost = await window.BGNJ_API.posts.get(postId);   // 서버는 { post: {...} } 를 준다
const ui = _serverPostToUi(fullPost);                        // → id: undefined 인 껍데기
this._serverPosts = this._serverPosts.map((p) =>
  String(p.id) === String(postId) ? ui : p                   // ← 목록의 그 글을 껍데기로 갈아치운다
);
```

글을 여는 순간 **그 글이 목록에서 지워지는 것과 같아진다.** 그래서 `find` 가 실패하고
'해당 게시글을 찾을 수 없습니다' 가 뜬다. 데이터는 멀쩡하고 화면 캐시만 망가진 것이다.

### 왜 지금까지 안 터졌나 — **내가 깨웠다**

이 결함은 **v00.170 부터 있었다.** 그런데 바로 위에 이런 가드가 있다.

```js
if (cached && cached.body && (cached.body.html || cached.body.text)) return;
```

목록 응답에 body 가 실려 있었으므로 **이 함수는 한 번도 끝까지 실행된 적이 없다.**
**v00.296.002 에서 목록의 body 를 빼자마자** 잠자던 코드가 깨어나 매번 실행되기 시작했다.

성능을 위해 데이터를 줄였더니, 그 데이터에 가려져 있던 버그가 드러난 것이다.

### 고친 것

- `res?.post || res` 로 벗겨낸다.
- **id 가 없으면 캐시를 아예 건드리지 않는다.** 못 받았을 때 지우는 것보다 그대로 두는 편이 낫다.
- 같은 형태를 전수 확인 — `books.get` 은 `direct?.book`, `columns.get` 은 `res?.column` 으로
  이미 올발랐다. **`posts` 만 잘못돼 있었다.**

검증: 실제 코드 텍스트를 떼어 Node 에서 돌렸다.
`{id:98,'목록의 글'}` → hydrate → `{id:98,'서버가 준 글', body:'<p>본문</p>'}` · **find 성공.**
조회가 실패하는 경로도 확인 — 기존 캐시가 그대로 남는다.

### 왜 '전체 점검' 에서 못 잡았나

**API 만 두드렸기 때문이다.** 이 버그는 서버가 아니라 브라우저 안에서만 산다.
API 응답은 처음부터 끝까지 정상이었다(글 89편 그대로, DB 와 완전 일치).
**브라우저 없이 하는 검증의 한계**를 정면으로 맞았다.

→ 이번처럼 **클라이언트 함수를 파일에서 떼어 Node 에서 돌리는 방식**이 유효했다.
   앞으로 캐시·상태를 다루는 함수는 이 방식으로 검증한다.

## 26. AI 가 스스로 검토할 수 있게 — 검사 장치 + AI·검색 창구 (v00.297.000)

**`tools/check-patterns.mjs`** — 오늘 실제로 사고를 낸 세 패턴.

**`tools/check-all.mjs`** — 여섯 검사를 한 번에. **각 검사가 왜 생겼는지(어떤 사고)까지 출력한다.**
목록 자체가 사고 기록이라 다음 사람이 맥락을 안다.

pre-commit 훅에 `check-patterns` · `smoke` 추가. CLAUDE.md 에 **'고치기 전에 반드시 알아야 할 함정' 5가지**를

|---|---|

   → `allLectures.length` 로 바꿨다. **'필터로 0건' 과 '정말 하나도 없음' 은 다르다.**
2. **필터를 만질 때마다 신청 정보를 통째로 다시 받을 뻔했다.** 신청 목록 prefetch effect 의
   deps 가 `lectures.length` 였다. → `allLectures.length`.
3. **빈 화면 문구를 갈랐다** — '관리할 강연이 없습니다' 와 '조건에 맞는 강연이 없습니다. 필터를 바꿔 보세요'.

`startsAt` 이 없으면 `next`('2026.05.09 · 토 20:00')에서 날짜만 건진다. 그것도 없으면
**정렬 방향과 무관하게 항상 맨 뒤**로 보낸다 — 오름차순에서 맨 앞에 뜨면 목록이 쓸모없어진다.
단, **필터에서 사라지지는 않는다**(전체 보기에는 그대로 나온다).

예정/지난/숨김/공개 필터, 일정 정렬 양방향, 일정 미정 위치, 검색, 신청·잔여 정렬,

## 28. 강연·투어 관리자 — 목록/세부 분리 + 참가 상태 3단계 (v00.299.000)

사용자 지시: '목록에서는 프로그램 명만, 클릭하면 세부 페이지 한 단계 더. 답사일정·준비물·커버·투어정보·
사진갤러리를 거기서 수정. 다른 탭에서 참가 신청 관리. 참가자는 신청/입금완료/참가확정 상태로. 강연도 동일.'

### 목록 → 세부 두 단계로

전에는 카드 하나에 **편집 폼 · 콘텐츠 편집 · 참가자 명단이 전부 펼쳐져** 있었다.
프로그램이 몇 개만 돼도 화면이 끝없이 길어진다.

- **목록** — 이름이 주인공. 부제·일정·장소는 작게, 오른쪽에 `신청 N` · `잔여 N/N`. 줄 전체가 버튼.
- **세부** — `← 목록으로` + 제목 + **두 탭**
  - **정보 · 콘텐츠** — 기존 편집 폼, 커버, 답사 일정/준비물, 사진 갤러리 (기존 기능 그대로)
  - **참가 신청 (N)** — 신청자 명단과 상태 관리

**기존 편집 기능은 하나도 건드리지 않았다.** 카드 안의 블록을 탭 조건으로 감싸기만 했다 —
큰 UI 재편에서 기능을 잃지 않는 가장 안전한 길이다.

목록 정렬·필터 툴바는 **목록에서만** 뜬다. 세부 화면에서는 의미가 없다.

### 참가 상태를 3단계로

| 상태 | 표시 | 뜻 |
|---|---|---|
| `pending_payment` | **신청** | 접수됨, 입금 대기 |
| `paid` | **입금 완료** | 돈은 확인됨, 확정 전 |
| `confirmed` | **참가 확정** | 최종 |
| `waitlist` / `refund_requested` / `cancelled` | 대기자 / 환불 신청 / 취소 | |

전에는 `pending_payment → confirmed` 한 번에 갔다. **돈은 들어왔지만 아직 확정 못 한 사람**을
구분할 방법이 없었다. 버튼도 흐름에 맞게 나눴다 —
신청: `[입금 확인]` `[바로 확정]` / 입금 완료: `[참가 확정]` `[되돌리기]` /
확정: `[확정 해제]` / 대기자: `[자리 배정]`.

상태는 색이 있는 칩으로 보인다(`StatusChip`).

**서버도 함께 고쳤다 — 이걸 빼면 정원이 새어 나간다.**
강연 정원 계산이 `status IN ('pending_payment','confirmed')` 였다. `paid` 를 안 넣으면
**입금한 사람이 자리를 차지하지 않은 것으로 세어 초과 접수된다.**
`paid_at` 도 `paid` 시점에 찍고, 알림 문구도 '입금 확인됨 / 확정됨' 으로 갈랐다(강연·투어 양쪽).

### 검증

스모크에 5개 추가(총 30개) — 세 단계 라벨, 모든 상태에 이름·색이 있는지,
그리고 **정원 계산에 `paid` 가 포함되는지**(빠지면 초과 접수되므로 문자열까지 직접 확인).

⚠ 워커 수정 중 치환 하나가 실패해 **A·B 가 적용된 내용이 통째로 롤백**된 적이 있다.
파이썬 스크립트에서 `assert` 가 예외를 던지면 `write` 까지 안 간다.
'수정 ok' 출력만 보고 넘어가면 안 된다 — **grep 으로 실제 파일을 확인**해야 한다.

## 29. 상세로 들어가면 바로 수정 (v00.299.001)

사용자 지적: '상세 페이지로 들어가면 정보를 바로 수정할 수 있게 해야지, 거기서 다른 단계가 추가되면 어떻게 하나.'

맞는 지적이었다. 28번에서 목록 → 상세로 한 단계를 만들었는데, 상세에서 **또 [수정] 을 눌러야**
폼이 열렸다. 단계를 줄이려고 만든 화면이 단계를 하나 더 늘린 셈이다.

### 고친 것

- **상세 진입 즉시 편집 상태.** `openDetail` 이 기본 정보 폼(`startEdit`)과
  답사 일정/준비물/커버(`startContentEdit`)를 함께 펼친다.
- **저장해도 폼을 닫지 않는다.** 닫으면 이어서 고칠 때 또 눌러야 한다.
  대신 '저장했습니다' 토스트로 결과만 알린다.
- **[취소] → [변경 되돌리기].** 상세에서는 폼을 닫지 않고 **입력값만 원래대로** 되돌린다.
  (목록 화면에서는 종전대로 '취소' 로 동작 — `detailId` 유무로 갈린다.)
- 카드 안의 `✎ 강연 정보` 버튼은 '편집 중이 아닐 때' 분기에 있어 상세에서는 자연히 사라진다.

'참가 신청' 탭 분리는 사용자가 좋다고 하여 그대로 둔다.

## 30. 정보 탭에서 갤러리·숨김·삭제가 사라져 있었다 (v00.299.002)

사용자 지적: '정보 탭에서 기존에 올라간 정보들이나 이미지들은 보여줘야지.'

### 내가 만든 회귀

v00.299.001 에서 상세 진입 시 곧바로 편집 상태가 되게 했다. 그런데 그 화면은
`{isEditing ? (편집 폼) : (작업 버튼 줄)}` 구조였다.

**늘 편집 상태 = else 분기가 영원히 안 나온다.** 그 안에 있던 것들이 통째로 사라졌다.

- 🖼 **포스터·현장사진** (갤러리 편집 진입로) — **접근할 방법이 없어졌다**
- 🙈 숨김 처리 / 표시 복원
- 삭제

→ 버튼 줄을 else 밖으로 꺼내 **늘 보이게** 했다. 삼항이 아니라 `&&` 가 된다.
   `✎ 정보` · `📋 진행·참고·커버` 버튼만 이미 열려 있을 때 숨긴다(중복 진입 방지).

### 정보 탭 맨 위에 '지금 등록된 것'

편집 폼만 띄우면 **무엇이 이미 있는지** 알 수 없다. 고치기 전에 현황부터 보여야 한다.

- 대표 이미지 미리보기 (없으면 '없음')
- 포스터 · 현장 사진 · 답사 일정(진행 순서) · 준비물(참고 사항) **개수**
- 사진 썸네일 최대 8장 + `+N`
- 사진이 없으면 '🖼 버튼으로 추가할 수 있습니다' 안내

강연은 `lecturePages`, 투어는 `tourPages` 에서 읽는다.

### 교훈

**`A ? (X) : (Y)` 에서 A 를 항상 참으로 만들면 Y 가 통째로 죽는다.**
조건을 바꿀 때는 반대편 분기에 무엇이 들어 있는지 먼저 봐야 한다.
오늘만 두 번째다 — 아침에도 `<window.X/>` 미등록으로 화면이 조용히 사라졌다.
**오류가 안 나는 실종**이 이 코드베이스에서 가장 흔한 사고 유형이다.

## 31. 대표 이미지 확대 · 관리자 주소 복원 · 크롤링 완전 차단 (v00.300.000)

사용자 지시 3건.

### ① 관리자 크롤링 차단 — 세 겹

`robots.txt` 를 다시 읽어 보니 **구멍이 있었다.**
`User-agent: *` 밑에 금지를 적어 뒀지만, **이름을 명시한 그룹(Googlebot·Yeti·GPTBot 등 17개)에는
그 규칙이 상속되지 않는다.** robots.txt 는 가장 잘 맞는 그룹 **하나만** 적용한다 —
이름을 적는 순간 `*` 규칙은 무시된다. 즉 **이름 붙은 크롤러 전부에게 관리자가 열려 있었다.**

- 18개 그룹 **모두**에 `Disallow: /admin` 외 6개를 명시했다.
- `Disallow: /admin$` 는 뺐다 — `$` 는 일부 크롤러만 아는 확장이고,
  `/admin` 은 접두사 매칭이라 `/admin/`·`/admin/xxx` 를 이미 다 포함한다.
- 관리자 화면에 들어와 있는 동안 `noindex, nofollow, noarchive, nosnippet, noimageindex`
  메타를 심는다(JS 를 실행하는 크롤러 대비). 나갈 때 제거.
- `seo-build` 에 **누출 검사** 추가 — sitemap 에 `/admin`·`/login`·`/mypage` 등이 섞이면 **빌드를 세운다.**
  목록을 손대다 실수할 수 있는 자리다.
- 세 번째 겹은 GitHub Pages 자체 — `/admin` 정적 파일이 없어 크롤러는 404 를 받는다.

### ② 대표 이미지 크게

120px 썸네일 → **360px, 원본 비율 유지**(`object-fit: contain`, 잘라내지 않는다).
이게 프로그램의 얼굴인데 작게 보면 확인이 안 된다. 사진 썸네일도 56 → 72px.

### ③ 새로고침해도 보던 자리로

관리자 화면은 주소가 늘 `/admin` 이라 **새로고침하면 무조건 대시보드로 튕겼다.**
→ `#admin=탭|상세id|하위탭` 으로 남긴다.

- 탭은 `AuthAdminPage` 가, 상세 두 칸은 각 패널이 관리한다.
- 해시를 고른 이유 — 서버 라우팅이 필요 없고 뒤로가기도 그대로 동작한다.
  기존 딥링크(`#col-`·`#post-`·`#lecture-`·`#tour-`)와 접두사가 겹치지 않는다.

**함께 막은 것** — 강연 탭에서 상세를 열어 둔 채 투어 탭으로 가면, 주소에 남은 id 를
투어 목록에서 못 찾는다. 그러면 상세도 목록도 안 나와 **화면이 텅 빈다.**
못 찾으면 조용히 목록으로 돌려보내는 가드를 두 패널 모두에 넣었다.

### 검증

스모크에 6개 추가(총 36개) — 해시 읽기/쓰기, 탭 부분 보존, 목록 복귀 시 상세 제거.

## 32. 대표 이미지 규칙 일치 + 지난 답사 후기 사진 (v00.300.001)

### ① 대표 이미지 — 관리자가 실제와 다른 것을 보고 있었다

사용자 질문: '대표이미지는 포스터 1번이 대표이미지 아니야?' **맞았고, 내가 틀렸다.**

### ② 지난 답사의 후기 사진 — 투어에만 없었다

사용자 지시: '지난 답사에도 사진이 올라가 있으면 그 사진들을 후기 사진으로 보여줘야지.'

`_isPast` 가 사용처와 같은 컴포넌트(`TourPage`) 스코프인지 — **문법 통과가 곧 동작은 아니다.**

## 35. 코드 기본값과 서버가 어긋난 곳 전수 정리 (v00.303.000)

사용자 지시: '그거 외에도 충돌하는 모든 것들을 정리해봐.'

`data.js` 의 `DEFAULT_*` 는 **서버(D1)가 응답하지 않을 때만** 쓰이는 폴백이다.
평소엔 서버 값이 덮어쓰므로 **어긋나 있어도 아무도 모른다.**
그러다 서버가 잠깐 느려지는 순간 엉뚱한 값이 화면에 뜬다.

### 실측으로 찾은 것

| 대상 | 상태 |
|---|---|
| **게시판** | ❌ 3건 어긋남 |
| 회원 등급 | ✅ (34번에서 이미 맞춤) |
| 도서 시드 | ⚠ 존재하지 않는 책 2권 |
| 한도 상수 | ⚠ 본문·제목이 화면에 없었다 |
| 사이트 문구 | 서버에만 있는 `hangyeon` 1건 — 무해 |

**게시판이 가장 나빴다.**

- `press`(언론보도) · `hangyeon-forum`(한켠역사문화포럼)이 **코드 기본값에 아예 없었다.**
  서버가 죽으면 그 두 게시판이 **통째로 사라진다.**
- 반대로 `column`(칼럼)은 **코드에만 있는 유령**이었다 — 서버에 그런 행이 없고
  칼럼은 `user_columns` 로 따로 관리된다. 지웠다.

**도서 시드**는 실제로 없는 책 두 권(`왕의길`·`다섯 봉우리 아래 읽는 조선`)을 들고 있었다.
서버에는 『왕의 길』 등 6권이 있다. 시드를 지우면 첫 페인트가 비므로 남기되,
**'화면 뼈대 확인용이고 판매 정보는 절대 여기서 읽지 않는다'** 를 주석으로 못 박았다.

### 한도 상수 대조 — 화면이 서버보다 느슨하면 안 된다

| 항목 | 화면 | 서버 |
|---|---|---|
| 첨부 개수 · 합계 · 이미지 수 | 3 · 10MB · 10 | 같음 ✅ |
| **제목 길이** | 120자 | 200자 (화면이 더 엄격 — 안전) |
| **본문 길이** | **없었다** | 200,000자 |

본문에 화면 제한이 없어 **긴 글을 다 쓰고 저장을 누른 뒤에야 거부**당했다.
같은 값을 화면에도 넣었다. **화면이 서버보다 엄격한 건 안전하고, 느슨하면 최악이다.**

제목은 입력칸에 `maxLength={120}` 이 박혀 있던 것을 상수로 끌어올렸다
(그대로 두면 서버 200과 어긋난 채 숨어 있게 된다).

### 재발 차단 — `tools/check-defaults.mjs`

코드의 `DEFAULT_*` 와 서버 실제값을 대조한다. 어긋나면 **어느 쪽에만 있는지까지** 알려준다.

- **네트워크가 필요**하므로 `check-all`(오프라인 보장)에는 넣지 않았다.
  배포 전이나 서버 데이터를 손댄 뒤에 따로 돌린다. CLAUDE.md 검증 명령에 추가했다.
- 서버에 닿지 못하면 **빌드를 세우지 않고** 건너뛴다 — 네트워크 문제로 작업이 막히면 안 된다.
- 만든 뒤 **일부러 라벨 하나를 어긋나게 해 잡히는 것을 확인**하고 원복했다.
