## 2. 자동 검사는 전부 통과했다 — 그래서 손으로 훑었다

`check-all` 7종 · `check-defaults`(게시판 6 · 등급 6 일치) 전부 초록.
빈 `catch` 도 0건이었다(v00.310 에서 이미 메웠다). **검사가 못 보는 자리 넷**을 찾았다.

### ① 늦게 온 답이 새 답을 덮는다 (가장 무겁다)

`refreshPosts` 는 **같은 옵션**끼리만 합친다. 옵션이 다르면 요청이 겹치고,
먼저 떠난 요청이 나중에 도착하면 옛 목록이 새 목록을 이긴다.
재시도가 600ms 씩 기다렸다 다시 묻기 때문에 실제로 자주 뒤집힌다.
**글을 쓰고 목록을 새로 받는 순간 걸리면 방금 쓴 글이 사라진 것처럼 보인다.**
낡은 요청의 *실패* 도 마찬가지로 새 요청의 성공을 지워 유령 오류를 띄웠다.
칼럼도 같다 — 관리자(`includeAll:true`)와 공개 화면이 같은 저장소를 채운다.

→ 요청마다 번호를 매기고 **적용 직전에 '내가 아직 최신인가'** 를 묻는다.

### ② 깨진 JSON 한 줄이 목록 전체를 죽인다

`rows.map(...)` 안에서 맨몸 `JSON.parse` 를 쓰고 있었다. 회원 한 사람의
`profile_json` 이 깨지면 **회원 목록 전체**가 실패로 떨어지고, `catch` 는
"기존 캐시 유지" 라고만 적는다 — 운영자는 왜 안 보이는지 알 길이 없다.
워커도 같아서, 한 행이 깨지면 엔드포인트가 통째로 500 이었다
(`categories_kv.prefixes_json` 이면 게시판 전체가 안 온다).

→ 양쪽에 `safeJson` / `_safeJson` — **깨진 행 하나만 버리고 로그를 남긴다.**
   ⚠ 워커에는 이미 같은 이름의 헬퍼가 있었다(로그를 안 남기는 판). 위로 올려 하나로 합쳤다.

### ③ 오류 기록이 무한히 커진다

`error_log` 는 **로그인 없이 누구나** 넣을 수 있는데(그래야 로그인이 깨져도 기록이 남는다)
자동 청소가 없었다. `page_views`·`audit_log`·`login_attempts`·`notifications` 는
전부 갖고 있는 장치다. **여기만 빠져 있었다.** 브라우저 오류 루프 하나면
하루에 수만 행이 들어오고, D1 이 차면 사이트 전체가 멈춘다.

→ 30일 보존 + 1/20 확률 GC. ⚠ **컬럼 이름을 조심할 것** — 이 표의 시각 컬럼은
   `created_at` 이 아니라 `ts` 다. `created_at` 으로 지웠다면 컬럼이 없어
   **조용히 아무것도 안 지우고 통과**했을 것이다(시험이 이걸 따로 지킨다).

### ④ 같은 신고가 무한히 쌓인다

관리자 '오늘 · 손볼 것' 은 `status='open'` 을 센다. 신고 버튼을 연타하면
그 숫자가 부풀어 **볼 것이 없는데 빨간 숫자**가 뜬다.

→ `INSERT ... SELECT ... WHERE NOT EXISTS` 로 원자화(CLAUDE.md 규칙).
   로그인 안 한 신고는 같은 사람인지 알 길이 없어 종전대로 넣는다.

## 7. 이어서 — v00.313.000 (전체개선 1회차)

백로그 `큐 1 · B` 의 **fire-and-forget 관리자 저장 sweep** 을 처리했다.

**관리자 패널이 서버 저장을 기다리지 않고 '저장되었습니다' 를 먼저 띄우고 있었다.**
저장 함수는 전부 `async` 인데 `await` 도 `.catch` 도 없다. 서버가 거절해도
화면은 성공이라 말한 뒤 목록만 다시 그린다 — 운영자는 저장된 줄 알고 창을 닫는다.
전역 `unhandledrejection` 이 토스트를 띄우긴 하지만 **초록 문구 다음에** 뜬다.
둘이 동시에 뜨면 사람은 앞의 초록을 믿는다.

→ 공통 관문 `window.BGNJ_ADMIN_SAVE`([AdminShared.jsx:1095](../../pages/admin/AdminShared.jsx#L1095)).
  끝난 뒤에만 성공을 말하고, 실패는 사람의 말로 알리고, 성공 여부를 돌려준다.
